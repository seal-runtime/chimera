Type Checking

By default, Luwu type checks your code in strict mode and reports mistakes in your editor as you write them. A file that needs to can opt out of strict checking. Values are still dynamically typed at runtime, and typing is gradual: you can start from untyped code, add type annotations a piece at a time and let inference handle most of the rest.

Catching mistakes

A typo in a field name is a type error, reported where you made it:

type Player = { name: string, level: number }

const function promote(player: Player)
    player.level += 1
end

promote({ name = "Ada", levl = 3 })
Typo: Did you mean 'level' instead of 'levl'?
TypeError: The given table is missing a property for 'Player':
  • 'level: number'

Without the checker, this program would fail later, when something reads the missing level.

Inference

Most code needs few annotations. Luwu infers the types of locals, return values and tables for you:

const function average(numbers: { number })
    local total = 0
    for _, n in numbers do
        total += n
    end
    return total / #numbers
end

const result = average({ 4, 8, 15 })
print(result)

Here only the parameter is annotated. total and the return value are inferred as numbers, and result is a number too.

Gradual typing

Untyped code still runs and still type checks. Its parameters accept anything until you annotate them:

const function label(name, count)
    return `{name} x{count}`
end

print(label("Potion", 3))

Adding annotations later tightens the checks without changing how the code runs:

const function label(name: string, count: number): string
    return `{name} x{count}`
end

print(label("Potion", 3))

To opt a file out of strict checking, put --!nonstrict or --!nocheck on its first line.

Annotations and the compiler

Type annotations also inform the compiler. Upstream Luau already uses them as optimization hints. Luwu goes further: in a file marked --!trust, the compiler relies on annotations to inline methods, and an annotation that doesn't match the actual value becomes a runtime error.

Error messages

Luau's type errors describe where the checker's subtyping test failed. Luwu's describe the mistake in terms of your code: the variable's name, the path to the bad property, and how to fix it when there's a common fix.

We purposely limit jargon in type errors. Terms like subtyping, variance or invariance stay out of a message unless it can't be understood without them. And when one is needed, we like to attach a "Help" explanation to describe what the term is and why we've flagged your code because of it.

Luwu names things the way your code does. Where Luau says "this" or expands a whole expanded type, Luwu uses the variable's name or the path to the property (like stool.inputs[i].count), or the type's alias.

Where possible, Luwu will try to add blue 'Info' notes (spans) to error messages to help you track down the root cause of a property mismatch, following it through multiple variables if needed. This means you don't have to manually trace error string paths back to where they came from.

The examples below were checked with upstream Luau 0.742's luau-analyze and with luwu-analyze. The output is unedited apart from the file name.

Typos

Luwu looks for typos wherever a name or a string is checked against a known set: locals, globals, properties, methods, library functions, type names, string literals and tagged union tags. Luau reports most of these as something else, like a missing property, or not at all.

Misspelled locals

A misspelled local:

--!strict
local player_name = "Ada"
print(player_nmae)
main.luau(3,7): TypeError: Typo 'player_nmae': Did you mean 'player_name'?
--!strict
local player_name = "Ada"
print(player_nmae)
main.luau(3,7): TypeError: Unknown global 'player_nmae'; consider assigning to it first

Unknown names

Luau reports every name it can't find as an unknown global, and suggests assigning to it. Luwu knows code rarely means to create a global, so it suggests defining a local instead. When there's a better explanation, Luwu gives that: a local used too early, one out of scope, or a module that was never required.

Undefined variables

A name used outside the function that defines it:

--!strict
local function load_save()
    local save_data = { level = 3 }
    return true
end

Tables

Things to know

  • Classes and traits are nominal types. Two classes with the same fields are still different types.
  • Validators check string literals, like colors or sizes, with your own error messages.
  • Type annotations describe values. They're separate from what type(x) returns.
